# 浏览器与电脑操作雷达

## 这个技能是做什么的

用户在做让 agent 使用浏览器的项目，想**广泛地搞懂这一整类系统的原理**：agent 使用浏览器和电脑（computer use）这个领域在发生什么，别人怎么让模型“看见”界面、怎么定位并操作、怎么接管浏览器或桌面、怎么处理登录态、可靠性、安全与评测。他们手动触发这个技能，每次得到某个 7 天窗口里的一份**偏专业、偏工程的学习笔记**。

**范围要广，不要只盯着用户自己的项目。** 用户明确说过，之前把范围收得太窄（只看与 yodo、TwoCursor 和录制演示相关的内容）。所以这个领域里有机制含量的东西都要收：不管它和用户的项目有没有关系。用户的项目只用来在文末给一小节可选的启发，不是收录标准，也不是每条内容的必填项。

它和另外两个雷达的关系：

| | harness-radar | app-radar | browser-radar |
|---|---|---|---|
| 目标 | 搞懂 Claude harness 原理 | 发现好玩的应用与项目 | 广泛搞懂浏览器与电脑操作的原理与工程取舍 |
| 信源 | 只收 Anthropic 人员署名内容 | 第三方、社区皆可 | GitHub、模型厂商与产品、工程博客、论文、技术讨论，不限作者，看一手程度与技术深度 |
| 形式 | 严谨的学习笔记 | 轻松的探索清单 | 严谨偏工程的学习笔记，每条都落到机制 |
| 取舍 | 宁少勿错，核实作者身份 | 多逛多看，核实真实存在 | 覆盖要广，但宁少勿浅，要读到实现层面，不停留在介绍 |

### 用户自己的项目（只用于文末的可选启发）

以用户在对话里最新说的为准。已知背景：

- **yodo**（github.com/yanggggjie/yodo）：用户先在浏览器里演示一遍任务，然后由 agent 照着去操作。
- **TwoCursor**（规划中的 skill/MCP 加浏览器扩展）：让人和 agent 在同一个浏览器里协作，把请求（必要时还有 DOM）记录成结构化数据，使人可以把做了一半的任务交给 agent。

用法：笔记写完之后，如果确实有内容对这两个项目有启发，在文末用一小节简短写出（见输出结构）。没有就写“本期没有特别相关的内容”，不要为了凑启发而硬扯关联，更不要因为和这两个项目无关就把一条好内容扔掉。

## 范围：什么算“浏览器与电脑操作的原理”

范围要宽，以机制为准，不以产品形态为准。涵盖浏览器 agent 和更一般的 computer use（桌面、移动端的 GUI agent）。常见主题（以实际材料为准，不要硬凑）：

- 页面与界面感知：DOM 序列化与裁剪、无障碍树（accessibility tree）、截图、带标记的截图（set-of-marks）、混合方案、内容压缩与分块；桌面场景下的屏幕截图、OS 级无障碍接口。
- 元素定位与动作落地（grounding）：给元素编号、选择器生成与稳定性、坐标点击与视觉定位、自愈式定位、iframe 与 shadow DOM 处理；视觉语言模型做 GUI grounding 的方法与数据。
- 控制通道：CDP（Chrome DevTools Protocol）、WebDriver BiDi、Playwright/Puppeteer、浏览器扩展、远程与云端浏览器、本地接管已有浏览器；桌面 computer use 的虚拟机、沙箱与输入注入。
- 模型与训练：面向 computer use 的模型能力、GUI agent 的训练数据与强化学习环境、合成轨迹、规划与执行分离、小模型执行器。
- 产品与架构：各模型厂商的 computer use 与浏览器 agent 产品（如 Anthropic、OpenAI、Google、微软等）、agentic 浏览器（把 agent 内置进浏览器的产品）、浏览器云厂商，它们的架构取舍与公开的设计说明。
- 会话与登录态：复用用户的 profile 与 cookie、隔离与持久化、多标签页与并行、凭据如何不经过模型。
- 网络层方法：请求录制与回放、把页面操作转成 API 调用、HAR、拦截与改写、从抓包生成工具。
- 演示学习与工作流沉淀：录制回放、把轨迹编译成脚本或 skill、轨迹泛化、参数化。这只是众多主题之一，不是重点。
- 人机协作与交接：共享会话、接管与归还控制权、状态同步、人的操作如何变成 agent 可读的上下文。
- 可靠性：等待与同步、页面稳定判定、重试、动作后验证、错误恢复、长任务的检查点。
- 上下文与成本：每步给模型多少信息、历史压缩、缓存、延迟与费用。
- 安全：页面里的提示注入（prompt injection）、权限与确认机制、沙箱与隔离、agent 权限模型。
- 反自动化与指纹：只在原理层面记录，不整理绕过 CAPTCHA 或检测的操作步骤。
- 评测：WebArena、Mind2Web、BrowserGym、WebVoyager、OSWorld 一类基准与自建评测，指标怎么定、失败怎么归因、基准本身的可信度。
- 行业动态里有机制含量的部分：重要的新版本、协议与标准的进展、有技术细节的事故与复盘。

下面这些只是**起点线索，不是结论**，现状与细节都要重新核实：browser-use、Stagehand、Playwright MCP、Chrome DevTools MCP、Skyvern、Midscene、LaVague、Nanobrowser，以及各大厂的 computer use 与浏览器 agent 产品。探索时要主动找清单之外的新项目。

## 时间窗口：一期一期往前推

各期窗口首尾相接：不重叠、不留缝，每期都是一份独立的新文档，绝不修改或覆盖旧期文档。

- 一期是 7 个自然日，起止日都算（如 10-22 至 10-28）。
- 文档标题格式固定：`浏览器控制雷达 · YYYY-MM-DD 至 YYYY-MM-DD`，仓库文件名格式固定：`browser-radar/YYYY-MM-DD_YYYY-MM-DD.md`。两者一起构成各期之间的“账本”，格式不要变。
- 先用时间工具取今天的日期，再按“存档：radar-notes 仓库”一节读出账本：仓库 `browser-radar/` 下的文件名，加上用 Claude Docs 的列表或查询能力（没有就用 Artifact 的 list）按标题前缀筛出的文档，取并集，读出各自起止日期。两边都列不出来，就用一句话问用户上一期的区间，别猜。

选下一期窗口：

- 用户说“往前推/上一期/再往前/前一周”：取已有最早一期的起始日 S，新窗口是 S 往前 7 天到 S 往前 1 天。
- 用户说“最新/这周”或什么都没说：新窗口是「最新一期结束日的后一天」与「今天往前 6 天」中较晚的那个，到今天。还没有任何一期就是今天往前 6 天到今天。账本已覆盖到今天，就按“往前推”处理并说明。最新一期离今天超过 7 天、中间会留缝时，照常做最近 7 天，告诉用户缺的区间，用户说“补上”再做。
- 用户给了明确区间：先和已有各期比对，有重叠就裁掉重叠部分并告诉用户。
- 一次要推多期：依次各做一份独立文档。
- 用户指定了方向（如“只看网络层方法”）或要“不限时间的专题”：标题里写明方向，不用固定格式，这类文档不算账本。
- **用户要求用新的（更广的）范围重做某个已经做过的窗口**：新建一份文档，标题在固定格式后加“（广泛版）”，例如 `浏览器控制雷达 · 2026-10-22 至 2026-10-28（广泛版）`。它不算账本，不影响后续窗口的计算，旧文档保留，不修改。开工前先读旧期的来源列表（优先读仓库里的 markdown），已经写过的项目不重复展开，只在新文档里一句话带过并指回旧文档，把篇幅留给旧文档因范围太窄而没收的内容。

### 什么算“出现在窗口里”

- 文章、论文、帖子：以首次发布日期算，回到原页面核实，不凭搜索摘要。
- 新项目：以仓库创建日、首个公开版本或首次发布算。
- 老项目与产品：窗口内有**机制层面的变化**才收，如新版本改变了页面表示方式、控制通道、定位策略、会话模型、模型能力或安全机制，或发布说明、重大 PR 里有值得拆的设计，标“（架构更新）”并写明版本、日期。只涨 star、修小 bug、改文档的不收。
- 同一个项目不要在相邻几期里反复作为主角出现；开工前读相邻一两期的来源列表（优先读仓库里的 markdown），已写过的只有新机制才再收。
- 往前推到较早窗口时，除出现日期外，还要核实**现状**：今天还活着吗（最近有提交）、设计是否已被后来的版本推翻、有没有被官方功能取代，写进每一条。

每个主题的延伸材料不受窗口限制，见第 5 步。

## 收录标准：看一手程度与技术深度

不限作者，不看和用户项目是否相关，但要能学到机制。按可信度和价值排序：

1. 源代码与设计文档：仓库里的核心实现、ARCHITECTURE、设计说明、RFC、协议规范与变更记录（CDP、WebDriver BiDi、W3C 无障碍相关规范等）。
2. 作者或团队写的工程博客、发布说明、系统卡与技术报告、演讲：说明为什么这样做、踩过什么坑。
3. 论文与基准的原始页面：以论文本身和官方仓库为准。
4. 有实质技术内容的社区讨论与第三方分析：可以收，但标明是第三方解读，不当作事实依据。

不收：营销软文、只有产品介绍没有机制的内容、纯 prompt 合集、转述他人内容的聚合文章、没有源码支撑的“逆向猜测”被当成事实写的内容。

**要读到实现层面**：对重点项目，不能只看 README。用 WebFetch 打开关键源文件或文档页（页面序列化、元素选择、动作执行、prompt 组织、会话管理等），看它具体怎么做。读不到实现就如实标“只读了介绍”，不要据此下机制结论。

不替用户克隆、安装或运行任何第三方代码，除非用户明确要求；读源码即可。对会读取登录态、cookie 或要求过宽权限的项目，在笔记里如实标出。

## 工作流程

### 1. 确定窗口

按上面的规则定好，并在回复里用一句话告诉用户这一期的区间。

### 2. 分渠道撒网

分渠道分别搜，一次大而全的查询效果不如分开搜。渠道提示，按情况增减，**覆盖要广**：

- GitHub：窗口内新建或发布的、与 browser agent、browser automation、computer use、GUI agent、CDP、MCP browser、record and replay、agentic browser 等相关的仓库；已知重要项目的发布页、合并的 PR、issue 里的设计讨论、ARCHITECTURE 或 docs 目录的变化。GitHub 搜索页常被禁止抓取，可以用 api.github.com 的 search/repositories 加 created 日期范围，再用 raw.githubusercontent.com 读源码。
- 模型厂商与产品：Anthropic、OpenAI、Google、微软、字节、阿里等的 computer use 与浏览器 agent 产品、发布说明、系统卡与技术报告；agentic 浏览器产品的更新与公开的设计说明。
- 工程博客与厂商文档：浏览器云厂商、自动化框架、Chrome 与 Chromium 开发者文档的更新、个人工程博客。
- 论文：arXiv 上 web agent、GUI agent、computer use、网页与桌面 grounding、GUI agent 训练与强化学习环境、评测相关的新论文；基准的新版本。arXiv 页面易被限流，可用 alphaxiv.org/abs/<id> 镜像取摘要与日期，请求之间留出间隔。
- 社区：Hacker News、Reddit、X、Linux.do、少数派、V2EX、掘金等有技术深度的讨论。
- 语言不限，中文英文都看，输出用中文。
- 搜索词带上月份或日期；窗口较早时换多种问法，多看按时间排序的页面。搜索引擎对“某一周”的限定几乎无效，主要靠直接抓各家博客列表页、发布页和 API 来核实日期。

任务较大时，如果有子代理工具，可以按渠道或主题并行派出（建议至少分成：GitHub、模型厂商与产品、工程博客、论文、社区），各自返回带链接、日期、读到的实现细节与证据等级的发现，由你汇总去重；没有就自己依次搜。搜索结果只是线索，要写进笔记的内容必须抓取原页面核对。子代理读到的细节，你没有亲自核对的，在笔记里如实标明。

### 3. 按机制归纳

把收集到的新内容按上面的主题分组。一个主题至少要有一条本期新内容才单独成节；零散的放进“其他”。不要为凑主题而硬分，也不要因为某个主题和用户的项目无关就不单独成节。

### 4. 给每条内容标注证据等级

- 读过源码：看了实现，能说清具体怎么做。
- 读过设计文档或博客：作者自己的说明。
- 只读了介绍或摘要：没有实现细节。
- 第三方解读：别人对它的分析。

另外区分**事实、设计理由、观点**：代码和文档里的行为是事实；作者解释取舍是设计理由；使用心得与预测是观点。互相矛盾时如实写出，不替用户选边。

### 5. 为每个主题补充延伸材料

每个主题成节之后，再针对它单独检索一轮高质量的相关材料，**不受 7 天窗口限制**，经典的实现、论文、博客都可以，必须标明发布日期，让用户分清本期新内容与延伸阅读。每个主题挑 2 到 4 条最值得读的，同样遵守收录标准。找不到合格的就写“未找到合格的延伸材料”。晚于本期结束日的内容尽量不放，确要放就标“本期之后发布”。

### 6. 提炼：这是怎么工作的

这是笔记的核心。对每条重点内容回答：

- 它要解决什么问题；
- **怎么做的**（机制层）：数据怎么表示、流程怎么走、关键的设计取舍是什么、代价是什么（成本、延迟、稳定性、权限）；
- 和已知做法相比是印证、补充还是对立；
- 想验证或深挖，下一步看什么（具体到仓库目录、文件、文档页，或一个可以做的小实验）。

看不出机制的条目，简要列出即可。宁可少而准，不要编造机制。和用户项目的关联不放在每一条里，统一放到文末的可选小节。

### 7. 挑出重点

挑出最多 3 条**最值得拆开读的**，说明读哪里、预计能学到什么；再用几句话总结这一期整个领域的走向。

## 输出：写成 Claude 文档

每一期**新建**一份文档，不要只在聊天里输出。优先用 Claude Docs（`mcp__Claude_Docs__*`）；具体调用方式以 Claude Docs 工具和 docs skill 的说明为准。定好窗口后，第一件正事是建好带固定标题与各节占位的骨架并打开给用户，然后一节一节填，每填一节前用一句话说在做哪一节，依赖全部结果的“本期概览”最后填。文档写作遵循 Claude Docs 的约定：每节第一句话就是结论，句子短，不用 emoji，不写“本文概述”之类的开场。

文档结构固定：

```
# 浏览器控制雷达 · <起始日期> 至 <结束日期>
<署名行：日期 · 作者>

## 本期概览
## <主题 1>
### 本期新内容
### 延伸材料
### 本主题小结
## <主题 2> ...
## 其他
## 最值得拆开读的 3 条
## 给你的项目的启发（可选）
## 待验证与存疑
## 来源列表
```

- 本期概览：3 到 5 句话，说这一期整个领域的走向、覆盖了哪些渠道、哪些没覆盖到、有几条因核实不过被剔除；较早窗口要说明“现状”按今天核实。
- 本期新内容每条包含：标题（带链接）、作者或团队、渠道、发布日期、证据等级、解决什么问题、怎么做的、关键取舍、和已知做法的关系、想深挖看什么。
- 延伸材料每条 2 到 3 行：标题、作者、渠道、日期、一句话说明为什么值得读。
- 给你的项目的启发（可选）：只在确实有关联时写，控制在一小节内，按“可直接借鉴 / 有冲突需权衡 / 值得做的小实验”简短分组，每条指回对应条目；没有就写一句“本期没有特别相关的内容”。
- 待验证与存疑：矛盾说法、没读到实现的细节、没核实的数据、覆盖缺口、值得做的小实验。
- 来源列表：按主题列出，格式 [标题](链接)，作者，渠道，日期，只列实际打开过的页面；由子代理打开、你没有核对的，注明。

标题和仓库文件名里的日期格式固定为 YYYY-MM-DD。每期同时在 radar-notes 仓库里存一份 markdown，见“存档：radar-notes 仓库”一节；“广泛版”和专题文档存进 `browser-radar/topics/`。Claude Docs 不可用时，只写仓库里的 markdown 文件，并用 SendUserFile 交给用户，同样不覆盖旧文件。

## 存档：radar-notes 仓库

每一期除了 Claude 文档，还要在用户的 GitHub 私有仓库 `yanggggjie/radar-notes` 里存一份内容相同的 markdown 文件。仓库有三个用途：跨期检索、让其他 agent 直接读文件、作为各期的账本。

仓库结构：

```
radar-notes/
  README.md
  harness-radar/2026-10-26_2026-11-01.md
  app-radar/...
  browser-radar/...
  <某个 radar>/topics/...
```

- 本技能的目录是 `browser-radar/`。每一期一个文件，文件名就是起止日期：`YYYY-MM-DD_YYYY-MM-DD.md`。
- 不算账本的文档（指定方向的专题、挖宝、“广泛版”重做等）放进 `browser-radar/topics/`，文件名用日期加简短的英文描述，例如 `2026-11-04_network-layer.md`。
- 已有文件不修改、不覆盖，每期都是新文件。

### 开工时（定窗口之前）

1. 用 add_repo 挂载仓库（owner `yanggggjie`，repo `radar-notes`，access `push`），按它返回的方式克隆到工作目录；本会话已经克隆过就执行 `git pull --rebase`。云端会话不保留上一次的文件，所以每个新会话都要重新克隆。
2. 仓库是空的（没有 README.md）时，先写一个 README.md，说明上面的目录结构、文件命名和“一期一个文件、不改旧文件”的规则，随本期文件一起提交。
3. 列出 `browser-radar/` 下的文件名（不含 `topics/`），读出已有各期的起止日期，这就是账本。
4. 仓库建立之前的旧期只存在于 Claude 文档里，所以同时按标题前缀 `浏览器控制雷达 · ` 列一遍用户的文档，两边取并集作为账本。
5. 读相邻一两期时（为去重、看来源列表），优先读仓库里的 markdown 文件，比读文档快。
6. 挂载或克隆失败时，把 add_repo 返回的原因原样告诉用户，改用文档标题作为账本，照常出文档，结束时说明这一期没有存进仓库。

### 收尾时（文档写完并核对之后）

1. 把文档的完整内容写成 `browser-radar/<起始日期>_<结束日期>.md`：先用 Claude Docs 的导出功能导出 Markdown；导出不可用时，按文档的同一结构和同一内容自己写。文件开头加元数据：

```
---
radar: browser-radar
window: <起始日期> 至 <结束日期>
doc: <Claude 文档链接>
created: <今天的日期>
---
```

2. 只 `git add` 这一个文件，提交说明写 `browser-radar: <起始日期> 至 <结束日期>`，结尾按会话给出的 attribution 行，然后 `git pull --rebase`，再 `git push`。
3. push 失败就重试一次；仍然失败，告诉用户原因，并用 SendUserFile 把这个 markdown 文件发给用户，保证内容不丢。

### 提到任何一期都附带链接

凡是提到某一期已经存在的笔记，都在旁边同时给出两个链接：Claude 文档链接，以及仓库文件链接 `https://github.com/yanggggjie/radar-notes/blob/main/<文件路径>`。适用于所有场合：结束时的回复、跨期检索的结果、文档里指回旧期或相邻期、说明窗口重叠或缺口时提到的已有期。

- 文档链接从仓库文件开头元数据的 `doc:` 读取，或从 Artifact 的 list 里按标题找；仓库链接按文件路径拼出，拼出后确认该文件确实已推送到仓库。
- 只有其中一个存在时，给出存在的那个，并写明另一个为什么没有（例如“未存进仓库：推送失败”“仓库建立前的旧期，尚未补存”）。
- 还没做的期（例如往前推的下一期）没有链接，只写区间。
- 不要只写日期区间或文件名而不给链接。

### 跨期检索

用户要跨期查找（例如“所有期里关于压缩的内容”“哪几期提到过 browser-use”）时，克隆或拉取仓库后用 grep 搜整个仓库（可以跨三个 radar 的目录），只读命中的段落，回答时每条命中都写明所在的期，并附上该期的仓库文件链接（尽量带到命中的行号，如 `#L42`）和 Claude 文档链接（在文件开头的元数据里）。这种情况只读不提交。

## 写作与引用的注意事项

- **原始材料链接就近给出**：正文里每条内容的标题，以及每个关于“怎么做的”的机制结论、关键取舍、延伸材料，都在该句或该条旁边直接放原始材料的链接（[页面名或文件名](链接)；读过源码的，链接到具体文件，能带行号或锚点就带上），读者不用翻到文末就能点开核对。理由：用户要靠源码和原文验证机制，链接离结论越近越好。一个结论依据多份材料，就在对应的那句话后各放各的链接。链接必须指向一手原始页面（源码文件、设计文档、官方博客、论文原页面），不放搜索结果页或转述页；没有打开过的页面不放链接；第三方解读要在链接旁标明“第三方解读”。文末“来源列表”仍保留，作为汇总。
- 用中文写，术语首次出现时在括号里保留英文。
- 转述，不整段照搬。必须引用原话时，单个来源最多一处、不超过 15 个英文单词，用引号标出并注明出处。代码片段、更新日志同样不整段复制，概括它做了什么。
- star 数、版本号、日期等数字回到原页面核对后再写，核对不了就写“未核实”。
- 搜不到就如实说：某主题没有新内容就写“本期无新内容”，整体较少就写“本期动态较少”，把少量内容认真做好，不用第三方转述补位。
- 没读到实现就不说“它是这样实现的”。
- 用户手动触发，不设定时任务，文档里不写“下期预告”。

## 结束时

聊天里只给一两句话：这一期的窗口区间，以及本期的 Claude 文档链接和仓库文件链接（各给一次，按“提到任何一期都附带链接”一节；没有存进仓库就写明原因）、最值得拆开读的一个发现、被剔除的条数。再提一句往前推的下一期是哪个区间。不要贴笔记内容，不要复述搜索过程。

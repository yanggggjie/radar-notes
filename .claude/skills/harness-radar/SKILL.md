# Claude Harness 雷达

## 这个技能是做什么的

用户的目标是**搞懂 Claude harness 的原理**，不是看热闹。他们会手动触发这个技能，想要的是：某个 7 天窗口里，Anthropic 的人对 harness 说了什么、做了什么，每条内容揭示了 harness 的什么机制，以及同一个主题下还有哪些值得一起读的材料。

输出是一份**按主题组织的学习笔记**，不是新闻清单。只说“发布了 X”而看不出机制的内容价值有限；拆解了 agent 循环、上下文压缩、权限设计的内容价值很高，哪怕它不算新闻。

这里的 harness 指围绕模型搭建的整套运行外壳：agent 循环、工具定义与调用、上下文窗口管理与压缩、权限与沙箱、子代理与并行、skills、MCP、hooks、memory、系统提示的组织方式、评测与可观测性等。范围要偏宽：和 Claude harness 设计取舍直接相关的 agent 工程实践也算。

## 什么内容可以收录

用户信任的是 Anthropic 里那些做出这些东西的人，以及他们的一手经验，不是公司的背书。所以收录标准看的是**作者是谁**，不是发布在哪里。

**收录**：Anthropic 人员本人署名或本人发布的内容，不论渠道：
- 官方渠道：官方博客与工程博客、claude.com 资源文章、claude.dev 上的文章、文档与更新日志、发布说明、官方 GitHub 仓库（包括维护者在 issue 和 PR 里的回复）。
- 个人渠道：员工的个人博客、X 等社交帖子、播客与视频访谈、会议演讲、能确认身份的社区发言（Hacker News、Reddit 等）。
- 论文：作者中有 Anthropic 人员、且署名单位写明 Anthropic 的。

**不收录**：媒体报道、第三方对官方内容的转述、解读和评论、非 Anthropic 作者的论文、社区的猜测、对源码或行为的第三方逆向分析。这些内容哪怕写得好、数据多，也不是用户要的东西，收进来只会稀释笔记。

**核实作者身份**：不要只凭文章自称。至少要有一条可靠证据：官方页面的署名与作者简介、作者本人账号资料写明在 Anthropic 工作、会议议程或播客节目介绍写明所属单位、论文署名单位。以**发布当时**是否在 Anthropic 任职为准，离职后写的不收。身份无法确认的一律不收，不要因为内容有价值就放宽；结尾告诉用户有几条因此被排除，由用户决定要不要再查。

## 工作流程

### 1. 确定时间窗口（每一期都是独立的 7 天）

每次运行产出的是**一期**：一个连续 7 天的窗口（含首尾，起止日期各算一天），生成一份**新文档**。各期文档互不覆盖，也不去改旧文档。

先用时间工具取今天的日期，再按下面的规则定窗口：

- **默认（最新一期）**：结束日 = 今天，起始日 = 今天往前 6 天。
- **向前推**：用户说“往前推”“上一期”“再往前”“前一周”之类，就接着已有各期往前排。先按“存档：radar-notes 仓库”一节读出账本（仓库文件名加文档标题），找出已有各期（标题形如“Claude Harness 雷达 · A 至 B”），取其中**起始日最早**的一期，新窗口 = 结束日为 A 的前一天、起始日再往前 6 天，这样各期首尾相接、没有缺口也没有重叠。列不出已有各期时，直接问用户上一期的起始日，不要猜。
- **用户指定了日期范围**：照用户说的来。若与已有某期重叠，告诉用户重叠的是哪几天，由用户决定是否照做。
- 窗口里每一天都要核实：搜索结果里经常混着其他日期的文章，窗口外的内容不算本期新内容。回溯较早窗口时，更新日志、官方博客页面的发布日期是最可靠的锚点。

主题延伸材料不受窗口限制，见第 5 步。

### 2. 收集新内容

分渠道分别搜索，一次大而全的查询效果不如分开搜：

- 先扫官方渠道：Anthropic 官方博客、工程博客、claude.com 资源与博客、文档与更新日志、Claude Code 与 Agent SDK 的发布说明和 GitHub 仓库、claude.dev 上的文章。
- 再从这些页面的署名里建立一份**作者名册**：谁写了什么、是什么角色。
- 然后用名册去查这些人的个人渠道：个人博客、X 帖子、演讲与播客、GitHub 上的活动。这是个人渠道里最可靠的找法，比按关键词在全网搜更能避开第三方内容。
- 语言不限，英文、中文、日文等都要看，但最终输出用中文。

任务较大时，如果有子代理工具，可以按渠道并行派出研究子代理，各自返回带链接、日期、作者与身份证据的发现，由你汇总去重。没有就自己依次搜。搜索结果只是线索，重要内容要抓取原文，确认日期、作者和内容，不要只凭摘要下结论。

### 3. 按主题归纳

把收集到的新内容按 harness 的机制主题分组。常见主题可以作参考，但以实际材料为准，不要为了凑齐主题而硬分：

上下文管理与压缩、子代理与编排、skills 与渐进式披露、工具与 MCP、权限与沙箱、hooks 与扩展机制、memory、评测与工程实践、模型能力与 harness 设计的关系。

一个主题至少要有一条本期新内容才单独成节；只有零散一两条、不成主题的，放进“其他”。这样每个主题都有内容可读，不是空架子。

### 4. 给每条内容标注来源类型和陈述类型

来源类型写清楚：官方渠道发布，还是员工个人渠道发布；作者是谁、什么角色、身份证据是什么。

陈述类型分三种，因为同样是 Anthropic 的人说的话，分量不一样：
- **事实陈述**：对系统行为的直接说明，如更新日志、文档、代码、发布说明。
- **设计理由**：作者解释为什么这样设计、取舍是什么。
- **经验或观点**：作者的使用心得、判断、预测。这是个人的判断，不等于系统的实际行为，也不代表公司立场，写笔记时要保持这个区别。

不同作者的说法互相矛盾，或者个人观点和文档事实不一致，如实写出来，不要替用户选边。

### 5. 为每个主题补充延伸材料

每个主题成节之后，再针对这个主题单独检索一轮 Anthropic 人员署名的相关材料。这一步**不受 7 天窗口限制**，可以是更早的文章、演讲和讨论，近期的优先，但必须标明发布日期，让用户分清哪些是本期新内容、哪些是延伸阅读。每个主题挑 2 到 5 条最有价值的，同样遵守收录标准和身份核实要求。找不到合格的就写“未找到合格的延伸材料”，不要用第三方内容凑数。

回溯较早窗口时，延伸材料可以与其他期重复出现，不用刻意回避；但**晚于本期结束日**的内容不要当作本期的新内容，也尽量少放进延伸材料，免得读起来像时间错乱。确要放，标注“本期之后发布”。

### 6. 提炼“这揭示了 harness 的什么机制”

这是笔记的核心，也是和普通新闻摘要的区别。对每条重点内容回答：
- 说了什么、做了什么（事实层）；
- 它说明了 harness 的哪个机制或设计取舍（原理层），例如上下文怎样被截断或压缩、工具结果怎样回填、权限怎样分级、子代理怎样隔离上下文；
- 和已知认知是印证、补充还是冲突；
- 想验证或深挖，下一步看什么（文档哪一页、仓库哪个目录、可以做的小实验）。

看不出机制的条目，简要列出即可，不要硬凑原理。宁可少而准，也不要编造机制。

### 7. 产出学习笔记文档

用户要求输出成**文档**。每一期**新建**一份文档，标题含本期起止日期，不复用、不覆盖、不修改此前任何一期。优先用 Claude Docs（`mcp__Claude_Docs__*` 工具），先建好带标题和各节占位的骨架并打开给用户，再逐节填充；每期同时在 radar-notes 仓库里存一份 markdown，见“存档：radar-notes 仓库”一节。Claude Docs 不可用时，只写仓库里的 markdown 文件，并用 SendUserFile 交给用户。聊天里只给一两句话概括和文档链接，不要贴整份笔记。

文档结构固定，方便用户每次用同样的方式阅读：

```
# Claude Harness 雷达 · <起始日期> 至 <结束日期>

## 本期概览
3-5 句话：这一周的主线是什么、最值得看的 2-3 条是什么。
写明覆盖范围、作者名册大概有多少人、哪些渠道没覆盖到，
以及有几条内容因为作者身份无法确认而被排除。

## <主题 1>
### 本期新内容
每条：标题、作者与角色、渠道、发布日期、陈述类型、
说了什么、揭示的机制、和已知认知的关系、想深挖看什么。
### 延伸材料
每条 2-3 行：标题、作者、渠道、日期、一句话说明为什么值得读。
### 本主题小结
把本节几条拼起来，说本期对这个机制的新增认知；没有就不写。

## <主题 2> ...（同上）

## 其他
不成主题的零散条目，每条一行，带作者、渠道、日期。

## 待验证与存疑
作者之间的矛盾、观点与事实不一致、没核实的细节、值得做的小实验。

## 来源列表
按主题列出，格式：[标题](链接)，作者，渠道，日期。
```

标题和仓库文件名里的日期格式固定为 YYYY-MM-DD，因为向前推时要靠它们识别已有各期。

## 存档：radar-notes 仓库

每一期除了 Claude 文档，还要在用户的 GitHub 私有仓库 `yanggggjie/radar-notes` 里存一份内容相同的 markdown 文件。仓库有三个用途：跨期检索、让其他 agent 直接读文件、作为各期的账本。

仓库结构：

```
radar-notes/
  README.md
  harness-radar/2026-10-26_2026-11-01.md
  app-radar/...
  browser-radar/...
  <某个 radar>/topics/...
```

- 本技能的目录是 `harness-radar/`。每一期一个文件，文件名就是起止日期：`YYYY-MM-DD_YYYY-MM-DD.md`。
- 不算账本的文档（指定方向的专题、挖宝、“广泛版”重做等）放进 `harness-radar/topics/`，文件名用日期加简短的英文描述，例如 `2026-11-04_network-layer.md`。
- 已有文件不修改、不覆盖，每期都是新文件。

### 开工时（定窗口之前）

1. 用 add_repo 挂载仓库（owner `yanggggjie`，repo `radar-notes`，access `push`），按它返回的方式克隆到工作目录；本会话已经克隆过就执行 `git pull --rebase`。云端会话不保留上一次的文件，所以每个新会话都要重新克隆。
2. 仓库是空的（没有 README.md）时，先写一个 README.md，说明上面的目录结构、文件命名和“一期一个文件、不改旧文件”的规则，随本期文件一起提交。
3. 列出 `harness-radar/` 下的文件名（不含 `topics/`），读出已有各期的起止日期，这就是账本。
4. 仓库建立之前的旧期只存在于 Claude 文档里，所以同时按标题前缀 `Claude Harness 雷达 · ` 列一遍用户的文档，两边取并集作为账本。
5. 读相邻一两期时（为去重、看来源列表），优先读仓库里的 markdown 文件，比读文档快。
6. 挂载或克隆失败时，把 add_repo 返回的原因原样告诉用户，改用文档标题作为账本，照常出文档，结束时说明这一期没有存进仓库。

### 收尾时（文档写完并核对之后）

1. 把文档的完整内容写成 `harness-radar/<起始日期>_<结束日期>.md`：先用 Claude Docs 的导出功能导出 Markdown；导出不可用时，按文档的同一结构和同一内容自己写。文件开头加元数据：

```
---
radar: harness-radar
window: <起始日期> 至 <结束日期>
doc: <Claude 文档链接>
created: <今天的日期>
---
```

2. 只 `git add` 这一个文件，提交说明写 `harness-radar: <起始日期> 至 <结束日期>`，结尾按会话给出的 attribution 行，然后 `git pull --rebase`，再 `git push`。
3. push 失败就重试一次；仍然失败，告诉用户原因，并用 SendUserFile 把这个 markdown 文件发给用户，保证内容不丢。

### 提到任何一期都附带链接

凡是提到某一期已经存在的笔记，都在旁边同时给出两个链接：Claude 文档链接，以及仓库文件链接 `https://github.com/yanggggjie/radar-notes/blob/main/<文件路径>`。适用于所有场合：结束时的回复、跨期检索的结果、文档里指回旧期或相邻期、说明窗口重叠或缺口时提到的已有期。

- 文档链接从仓库文件开头元数据的 `doc:` 读取，或从 Artifact 的 list 里按标题找；仓库链接按文件路径拼出，拼出后确认该文件确实已推送到仓库。
- 只有其中一个存在时，给出存在的那个，并写明另一个为什么没有（例如“未存进仓库：推送失败”“仓库建立前的旧期，尚未补存”）。
- 还没做的期（例如往前推的下一期）没有链接，只写区间。
- 不要只写日期区间或文件名而不给链接。

### 跨期检索

用户要跨期查找（例如“所有期里关于压缩的内容”“哪几期提到过 browser-use”）时，克隆或拉取仓库后用 grep 搜整个仓库（可以跨三个 radar 的目录），只读命中的段落，回答时每条命中都写明所在的期，并附上该期的仓库文件链接（尽量带到命中的行号，如 `#L42`）和 Claude 文档链接（在文件开头的元数据里）。这种情况只读不提交。

## 写作与引用的注意事项

- **原始材料链接就近给出**：正文里每条内容的标题，以及每个事实、设计理由、机制结论、延伸材料，都在该句或该条旁边直接放原始材料的链接（[原文标题或页面名](链接)，能定位到具体章节、文件或锚点就带上），读者不用翻到文末就能点开核对。理由：用户要靠原文验证机制，链接离结论越近越好。一条内容引用了多份材料，就在对应的那句话后各放各的链接。链接必须指向一手原始页面（官方页、原帖、原文档、仓库文件），不放搜索结果页或转述页；没有打开过的页面不放链接；确实没有可链接的原始材料（如播客里的一句话）就写明出处和时间点。文末“来源列表”仍保留，作为汇总。
- 用中文写，术语首次出现时在括号里保留英文原文。
- 转述原文，不整段照搬。必须引用原话时，单条来源最多一处、不超过 15 个英文单词，用引号标出并注明出处。更新日志条目、代码片段同样不整段复制，概括它做了什么。
- 日期、版本号、数字容易出错，回到原文核对后再写，核对不了就写“未能核实”。
- 搜不到就如实说。本期没有合格内容的主题，直接写“本期无新内容”；整体很少时，写“本期动态较少”，把少量内容认真做好。不要用第三方内容补位。
- 用户自己触发，不设定时任务，文档里不写“下期预告”。

## 结束时

回复用户：本期窗口的起止日期，以及本期的 Claude 文档链接和仓库文件链接（按“提到任何一期都附带链接”一节；没有存进仓库就写明原因）、一两句话概括本期最值得看的发现、有几条内容因为作者身份无法确认而被排除（用户想查可以再让你查）、哪些主题的延伸材料不足。不要复述搜索过程。

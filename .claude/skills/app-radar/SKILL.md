# Claude 场景实现雷达

## 这个技能是做什么的

用户在把 Claude Agent SDK 部署成后端业务服务。他想看的是**具体场景里的 harness 实现**：有人把 Claude 的 harness（Agent SDK、Claude Code 的无头模式与 SDK 化用法）做成了某个具体的东西，比如某个业务的客服机器人、端到端（E2E）测试机器人、代码评审机器人、数据分析 agent、运维值班 agent，并且**公开了能看的实现**：代码仓库，或者足够详细的技术报告。

他不要的是宏大叙事：合作伙伴关系、采购协议、行业趋势、“某公司全员接入 Claude”、没有实现细节的客户成功故事。判断一条材料值不值得收，只问一句话：**读完之后，我能不能照着做出一个类似的东西？**

每次的成果是一份 Claude 文档，外加 radar-notes 仓库里一份内容相同的 markdown，一期一份，按时间窗口首尾相接，用户可以一周一周往前翻。

和 harness-radar 的区别：harness-radar 研究 harness 的原理，只收 Anthropic 人员署名的内容；app-radar 看别人用 harness 做出了什么具体的东西，信源不限，但必须带实现。

## 收录门槛：必须有实现

一条案例至少满足下面之一，才进主清单：

- **有代码**：公开仓库（含 README 与关键源码），或文章里贴出了足以看懂结构的代码。
- **有详细技术报告**：工程博客、论文、大会演讲，写清了 harness 怎么用的，至少回答这几件事中的大部分：用的是 Agent SDK、Claude Code 无头模式还是裸 API；系统提示与技能（skills）怎么组织；接了哪些工具与 MCP；权限与沙箱怎么配；会话与上下文怎么管；人工介入点放在哪；怎么评测；怎么部署与调度。

没有实现细节的，不进主清单，放进“被剔除与存疑”并写明原因。

**收的场景**（举例，不是清单）：客服与工单机器人、端到端与回归测试机器人、代码评审与 PR 机器人、故障排查与 SRE 值班、数据分析与报表、文档与知识库问答、迁移与重构自动化、安全分析、内容审核、销售与 CRM 自动化、财务对账。形态不限：开源仓库、公司工程博客、大会演讲、论文、个人写的详细实践文章。

**不收**：新闻稿、合作伙伴公告、采购与定价新闻、泛泛的客户案例页（只有“节省了 X% 时间”而没有实现）、界面换肤与第三方客户端、通用聊天壳、纯 prompt 合集、只说“接入了 AI”看不出用的是 Claude 的报道。Anthropic 自家新产品最多在概览里一句话带过。

## 时间窗口：一期一期往前推

各期窗口首尾相接：不重叠、不留缝，每期都是独立的新文档。

- 一期是 7 个自然日，起止日都算。用户要求的第一期可以不足或超过 7 天，之后都按 7 天算。
- 文档标题格式固定：`Claude 场景实现雷达 · YYYY-MM-DD 至 YYYY-MM-DD`，仓库文件名格式固定：`app-radar/YYYY-MM-DD_YYYY-MM-DD.md`。两者一起构成各期之间的“账本”，格式不要变。
- 账本只认这个前缀。旧前缀（`Claude 行业应用雷达`、`Claude 周边应用雷达`）属于旧范围，不算已覆盖，但开工前可参考其中的项目名去重。
- 先用时间工具取今天的日期，再按“存档：radar-notes 仓库”一节读出账本：仓库 `app-radar/` 下的文件名，加上用 Artifact 工具的 list 按前缀筛出的文档，取并集，读出各自的起止日期。两边都列不出来，就用一句话问用户上一期的区间，别猜。

怎么选下一期的窗口：

- 用户说“往前推/上一期/再往前/前一周”：取已有最早一期的起始日 S，新窗口是 S 往前 7 天到 S 往前 1 天。
- 用户说“最新/这周”或什么都没说：新窗口是「最新一期结束日的后一天」与「今天往前 6 天」中较晚的那个，到今天。还没有任何一期，就是今天往前 6 天到今天。账本已覆盖到今天，就按“往前推”处理并在回复里说明。最新一期离今天超过 7 天会留缝：照常做最近 7 天，并告诉用户缺的区间。
- 用户给了明确区间：先和已有各期比对，有重叠就裁掉并告诉用户。
- 一次要推多期：依次各做一份独立的新文档。
- 绝不修改或覆盖旧期文档，每次都新建。
- 用户指定了场景（如“只看客服机器人”）或要“挖宝/不限时间”：标题里写明场景或“挖宝”，不用固定格式，不算账本。

### 什么算“出现在窗口里”

- 以**首次公开**的日期算：文章发表日、演讲日、仓库创建日或首次公开提交日。日期必须回到原页面核实，不能凭搜索摘要。
- 老仓库或老文章在窗口内有重大更新（新架构、新版本、新的详细报告），可以收，标“（新进展）”并写清日期。其他窗口外的不进清单，特别值得一提的在概览里一句话带过。
- 开工前看相邻一两期的来源列表（优先读仓库里的 markdown），已出现过的不重复推荐。
- 往前推到较早的窗口时，要核实“现状”：仓库今天还在维护吗，有没有归档、改名，文章里的做法是否已被 SDK 新版本取代，写进每一条。

## 工作流程

### 1. 撒网：按场景搜，重点找代码和技术报告

每个场景分别搜，一两个查询，不要一次大而全。渠道提示：

- **代码托管**：GitHub 上用 Claude Agent SDK、claude-agent-sdk、`claude -p` 无头模式、Claude Code GitHub Action 做具体事情的仓库；按场景词搜，如 support bot、E2E test agent、PR review、incident、triage。看创建时间、提交记录、README 里的架构图和运行方式。
- **工程博客与技术报告**：公司工程博客、个人详细实践文章、大会演讲与幻灯片、论文。
- **社区**：Hacker News、Reddit、Product Hunt 里附带仓库或详细复盘的帖子。
- **官方**：Anthropic 的工程博客、Agent SDK 文档与示例仓库、客户案例页中真正带架构细节的那几篇。
- 语言不限，中文英文都看，输出用中文。搜索词带上月份或日期；窗口较早时多换问法，多看按时间排序的页面。

任务较大时，如果有子代理工具，可按场景并行派出，各自返回带链接和日期的发现；没有就自己依次搜。搜索结果只是线索，写进文档的案例必须抓取原页面确认。

### 2. 核实与筛选

用户要拿这些实现当参照去做自己的服务，一个夸大或根本没有实现的“案例”比少写几个更糟。每一条过这几关：

- 首次公开日期在窗口内，链接能打开。
- **确实用了 Claude harness**：仓库依赖或文章明确写出用了 Agent SDK / Claude Code。只能从第三方转述得知的，标“转述”。
- **实现材料读过**：仓库要实际看 README 与关键源码（入口、系统提示或技能、工具与权限配置、会话管理）；技术报告要读全文。只看了标题和摘要的，不进主清单。
- **真实性分级**：生产在用 / 内部使用 / 个人实验 / 演示。依据写出来（有真实用户、有运行日志、有 issue 与提交活跃度）。开源仓库看 star 之外的证据：提交频率、issue、是否有人在用。
- **成效数字带出处并写明是谁说的**；没有基线的数字只当自称转述，核对不了写“未核实”。
- **安全与权限**：这类 agent 通常能执行命令、访问内部系统，仓库里的权限模式（允许哪些工具、是否绕过权限确认、沙箱隔离、密钥处理）要如实写出；有明显风险（如默认跳过权限确认、把密钥写进提示）直接标出。
- 涉及要装进用户环境的 MCP 或插件，留意权限、来源与是否开源。

不替用户安装或运行任何第三方东西，除非用户明确要求。

### 3. 归类

按**场景**分组（客服、E2E 测试、代码评审、运维……），不按行业分。只有一条的场景并进“其他场景”。

### 4. 每条怎么写（短，但信息要密）

- 名称（带仓库或文章链接）与场景，以及首次公开日期、现状
- **它做什么**：一两句话，谁用、替代哪个流程、输入输出是什么
- **harness 怎么用的**：这是核心。写 Agent SDK 还是 Claude Code 无头模式、入口怎么调用、系统提示与技能怎么放、接了哪些工具与 MCP、权限模式与沙箱、会话与上下文管理、人工介入点、评测与回放、部署与调度。没披露的写“未披露”，不要猜
- **关键实现**：指出读哪几个文件或哪几段，必要时贴一小段关键代码（几行，标出文件路径与链接），让读者知道结构长什么样。只摘最能说明结构的，不整段搬
- **成效与真实性**：数字加出处加是谁说的；真实性分级与依据
- **能否复刻**：读完后，自己照着做需要补什么、有什么坑
- **证据等级**：读过代码与文档 / 读过完整技术报告 / 只看了转述

### 5. 横向提炼与挑重点

看本期实现有没有共通的结构，例如客服机器人怎么划分工具权限、测试机器人怎么拿到浏览器、会话怎么持久化、怎么回放评测、怎么控制成本。有就写，没有就不写。

最后挑出 **3 个最值得深读的**，说明为什么（实现细节完整、可跑、与用户的后端服务场景接近）。

## 输出：写成 Claude 文档

成果是一份新的 Claude 文档，不要只在聊天里输出。建文档的具体调用方式以 Claude Docs 工具和 docs skill 的说明为准。

- 定好窗口后，第一件正事就是建文档骨架：标题（固定格式）、署名行，以及每一节一个待填占位，并马上打开给用户看。研究发现写进文档，不贴在聊天里。
- 然后一节一节填，每填一节前用一句话告诉用户在做哪一节。依赖全部结果的“本期概览”最后填。
- 每节第一句话就是结论，句子短，不写“本文概述”之类的开场，不用 emoji。

文档结构固定：

```
# Claude 场景实现雷达 · <起始日期> 至 <结束日期>
<署名行：日期 · 作者>

## 本期概览
## <场景 1>
## <场景 2> ...
## 本期共通的结构
## 最值得深读的 3 个
## 被剔除与存疑
## 来源
```

- 本期概览：两三句话说这一期有哪些场景、几条带完整实现，覆盖了哪些渠道、哪些没覆盖，几条因没有实现细节被剔除。较早窗口说明“现状”是按今天核实的。
- 场景小节：每个实现一小段，按“每条怎么写”的字段，没有信息的字段省略，只有“harness 怎么用的”和“成效”缺失时明说“未披露”或“未核实”。
- 本期共通的结构：没有就整节省略。
- 被剔除与存疑：每条一行，名字加原因（没有实现细节、只有新闻稿、日期对不上、看不出用了 Claude、核实不过）；数量多就合并成一句。
- 来源：[标题](链接) 的列表，只列实际打开过的页面。

案例总量 4 到 8 条为宜，宁少而真。语气平实、具体，像工程师写给工程师的调研笔记。用中文写，术语首次出现时在括号里保留英文。

每期同时在 radar-notes 仓库里存一份 markdown，见“存档：radar-notes 仓库”一节。Claude Docs 不可用时，只写仓库里的 markdown 文件，并用 SendUserFile 交给用户，同样不覆盖旧文件。

## 存档：radar-notes 仓库

每一期除了 Claude 文档，还要在用户的 GitHub 私有仓库 `yanggggjie/radar-notes` 里存一份内容相同的 markdown 文件。仓库有三个用途：跨期检索、让其他 agent 直接读文件、作为各期的账本。

仓库结构：

```
radar-notes/
  README.md
  harness-radar/2026-10-26_2026-11-01.md
  app-radar/...
  browser-radar/...
  <某个 radar>/topics/...
```

- 本技能的目录是 `app-radar/`。每一期一个文件，文件名就是起止日期：`YYYY-MM-DD_YYYY-MM-DD.md`。
- 不算账本的文档（指定方向的专题、挖宝、“广泛版”重做等）放进 `app-radar/topics/`，文件名用日期加简短的英文描述，例如 `2026-11-04_network-layer.md`。
- 已有文件不修改、不覆盖，每期都是新文件。

### 开工时（定窗口之前）

1. 用 add_repo 挂载仓库（owner `yanggggjie`，repo `radar-notes`，access `push`），按它返回的方式克隆到工作目录；本会话已经克隆过就执行 `git pull --rebase`。云端会话不保留上一次的文件，所以每个新会话都要重新克隆。
2. 仓库是空的（没有 README.md）时，先写一个 README.md，说明上面的目录结构、文件命名和“一期一个文件、不改旧文件”的规则，随本期文件一起提交。
3. 列出 `app-radar/` 下的文件名（不含 `topics/`），读出已有各期的起止日期，这就是账本。
4. 仓库建立之前的旧期只存在于 Claude 文档里，所以同时按标题前缀 `Claude 场景实现雷达 · ` 列一遍用户的文档，两边取并集作为账本。
5. 读相邻一两期时（为去重、看来源列表），优先读仓库里的 markdown 文件，比读文档快。
6. 挂载或克隆失败时，把 add_repo 返回的原因原样告诉用户，改用文档标题作为账本，照常出文档，结束时说明这一期没有存进仓库。

### 收尾时（文档写完并核对之后）

1. 把文档的完整内容写成 `app-radar/<起始日期>_<结束日期>.md`：先用 Claude Docs 的导出功能导出 Markdown；导出不可用时，按文档的同一结构和同一内容自己写。文件开头加元数据：

```
---
radar: app-radar
window: <起始日期> 至 <结束日期>
doc: <Claude 文档链接>
created: <今天的日期>
---
```

2. 只 `git add` 这一个文件，提交说明写 `app-radar: <起始日期> 至 <结束日期>`，结尾按会话给出的 attribution 行，然后 `git pull --rebase`，再 `git push`。
3. push 失败就重试一次；仍然失败，告诉用户原因，并用 SendUserFile 把这个 markdown 文件发给用户，保证内容不丢。

### 提到任何一期都附带链接

凡是提到某一期已经存在的笔记，都在旁边同时给出两个链接：Claude 文档链接，以及仓库文件链接 `https://github.com/yanggggjie/radar-notes/blob/main/<文件路径>`。适用于所有场合：结束时的回复、跨期检索的结果、文档里指回旧期或相邻期、说明窗口重叠或缺口时提到的已有期。

- 文档链接从仓库文件开头元数据的 `doc:` 读取，或从 Artifact 的 list 里按标题找；仓库链接按文件路径拼出，拼出后确认该文件确实已推送到仓库。
- 只有其中一个存在时，给出存在的那个，并写明另一个为什么没有（例如“未存进仓库：推送失败”“仓库建立前的旧期，尚未补存”）。
- 还没做的期（例如往前推的下一期）没有链接，只写区间。
- 不要只写日期区间或文件名而不给链接。

### 跨期检索

用户要跨期查找（例如“所有期里关于压缩的内容”“哪几期提到过 browser-use”）时，克隆或拉取仓库后用 grep 搜整个仓库（可以跨三个 radar 的目录），只读命中的段落，回答时每条命中都写明所在的期，并附上该期的仓库文件链接（尽量带到命中的行号，如 `#L42`）和 Claude 文档链接（在文件开头的元数据里）。这种情况只读不提交。

## 写作与引用的注意事项

- **原始材料链接就近给出**：每条案例里，名称带仓库或原文链接，“harness 怎么用的”“关键实现”“成效与真实性”里的每个事实（源码文件、文档、博客、演讲、数字、日期等），都在该句旁边直接放对应原始页面的链接，读者不用翻到文末就能点开核对。指向具体文件时用仓库里的文件链接。链接必须指向一手原始页面，不放搜索结果页或转述页；没有打开过的页面不放链接。文末“来源”仍保留作汇总。
- 转述，不整段照搬。贴代码只贴说明结构所需的几行，并注明出处与许可（许可证不明确就只描述不贴）。必须引用文字原话时，单个来源最多一处、不超过 15 个英文单词。
- 数字（成效、规模、日期、star 数）回到原页面核对后再写，核对不了就写“未核实”。
- 搜不到好实现就如实说“这段时间动静不大”，认真做好少量几条，不要凑数，更不要拿宏大的公告补位。
- 不夸大；没有一手证据就不说“已大规模落地”。
- 不收集或写入个人隐私信息；案例里的个人只写到角色层面。
- 用户手动触发，不设定时任务，不写“下期预告”。

## 结束时

聊天里只给一两句话：这一期的窗口区间，以及本期的 Claude 文档链接和仓库文件链接（各给一次，按“提到任何一期都附带链接”一节；没有存进仓库就写明原因）、最值得看的一个实现、被剔除的条数。再提一句往前推的下一期是哪个区间。不要贴清单，不要复述搜索过程。

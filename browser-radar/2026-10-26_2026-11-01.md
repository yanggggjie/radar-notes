## 本期概览

本期可以读到实现层的条目很少，多数只读到 README、PR 正文或论文摘要。走势上有三点：第一，评测规则本身被当作变量来测量，Odysseys2 同一批尝试换评分器后分数从 77–96 变成 2–85，Right Click, Wrong Box 指出框内判定会把等价点击当成错误；第二，点击失效的来源被测量为页面加载而不是规划间隔，等待约 1 秒网络静止就能消除大部分（摘要自报）；第三，控制通道上出现几个扩展加本地 relay 的开源实现，其中 anomalyco/browse 写明了 cookie 读写边界，pw-repl 让人和 agent 在同一个会话里发相同的命令。另外两家模型厂商在同一周的文档里分别把 Computer Use 工具 GA（Gemini，10-30）和把写代码执行列为主路径（OpenAI，10-26 changelog）。

**[AdaGround：按目标尺寸放大，并用验证器复核的免训练落点方法](https://arxiv.org/abs/2610.36874)** Bingchao Wang 等 · 论文 · 2026-10-27 09:12 UTC（papers.cool 标注）· 证据：我读过摘要页，未读全文。

- 问题：高分辨率屏幕上小目标最容易定位失败。已有的免训练放大方法对所有目标用同一放大倍率，并且无条件接受放大后的答案。
- 做法（摘要所写）：模型先估计目标大小，据此为每个样本设定放大倍率、视野和放大层数。一个看到“带标记点击”的是/否验证器决定接受还是拒绝每次放大，在多条放大链之间选择，触发重新定位，并通过“目标是否存在”的查询决定放弃。表格单元格按表头组合定位。
- 结果（摘要自报）：在 Qwen3-VL 上，OSWorld-G 与 ScreenSpot-Pro 比骨干模型提高 7.4 至 20.6 个百分点，并迁移到未参与调参的 UI-Vision。
- 代价：多轮放大加验证意味着更多次模型调用，摘要没有给延迟。验证器放弃的判据在摘要里没有展开。
- 深挖：[代码仓库](https://github.com/bcwang-sjtu/AdaGround)（页面给出，我没有打开）。

**[Right Click, Wrong Box：按“点击产生的结果”给 GUI grounding 评分](https://arxiv.org/abs/2610.36831)** Xiaokang Yuan 等 · 论文 · 2026-10-27 08:30 UTC · 证据：我读过摘要页，未读全文。

- 问题：ScreenSpot-v2 只把落在标注框内的点击算对，但界面常用多个元素触发同一个动作，例如重复的链接、复选框的标签、徽标旁的标题。
- 做法（摘要所写）：在真实 Web 应用的每个页面上执行并指纹化约 1000 次点击，得到“结果图”和执行判定器。点击正确的定义改为：它产生的结果与标注目标产生的结果相同。不需要新增标注。
- 结果（摘要自报）：被框评分判错的点击中，约五分之一（代码托管站）和三分之一（网店）实际达到了目标结果。对 ScreenSpot-v2 的审计修正为 0.2 至 1.8 个百分点，与领域内报告的模型差距同一量级。在 3B 模型的 GRPO 实验里，把等价点击计入奖励，在三个随机种子、四个测试集上没有得到稳定提升。
- 代价：只验证了两个站点；探针与预测数据按摘要承诺发布，页面没有给出链接。

**[What Does "Now" Mean to Your Computer-Use Agent?：点击过期的来源是页面加载，不是规划间隔](https://arxiv.org/abs/2610.39282)** Vasundra Srinivasan · 论文 · 2026-10-29 03:33 UTC · 证据：我读过摘要页（摘要文本在某一句中被截断），未读全文。

- 问题：agent 基于截图规划数秒后再点击，页面在这段时间里变化，点击就落到错误的元素上。以往工作把规划间隔当作风险来源。
- 测量（摘要自报）：在31个公开网页上，页面完全加载后规划的点击有30秒内失效的比例是0.4%；页面打开后第一秒内规划的点击是17%。等待约1秒让网络活动停止，就能消除大部分风险。
- 检查方法（摘要自报）：在不可逆操作前、页面仍在加载时做点击前检查。像素比较验证目标位置，精度与前沿视觉语言模型相当，延迟为其八分之一；验证上一步是否成功，4B 模型与前沿模型相当。
- 存疑：摘要写“八个广泛使用的开源智能体中，有十个的等待规则仍使超过 1% 的点击失效”，分子大于分母，不自洽，我不引用这个数。
- 深挖：[preflight-bench](https://github.com/multimodal-ai-engineering/preflight-bench)（页面给出，未打开），摘要称它包含基准生成器、判断检查是否值得的盈亏平衡公式和三条规则。

**[Stagehand #3339：接管已存在的和嵌套的跨域 iframe](https://github.com/browserbase/stagehand/pull/3339)** seanmcguire12（接续 #3262）· Browserbase Stagehand · created 2026-10-28T19:19Z，merged 2026-10-29T17:17Z（API 字段）· 证据：我读过 PR 正文（经摘要转述），未读源码。

- 问题：`BrowserContext` 只在两种情况下接管跨进程 iframe（OOPIF）的 CDP 会话：子 iframe 的主帧已在页面帧图里，或父会话后来发出 `Page.frameAttached`。重连、扩展 service worker 重启时已经加载好的 iframe，以及嵌套在另一个 OOPIF 里的 OOPIF，都收不到这个事件，子会话一直停在 `pendingOopifByMainFrame` 里，快照和 `act` 看不到 iframe 内部。
- 做法：子会话 attach 时，用它自己的 `Page.getFrameTree` 找到父帧 id，回退到拥有该父帧的页面；页面还没注册就记下父帧 id，等页面注册、父 OOPIF 被接管或 `frameAttached` 到达时重试。已接管的 OOPIF 会话按帧登记，子会话存活期间，父会话迟到的 `frameAttached` 不再改变归属。逻辑拆成 `findPageOwningFrame` 和 `adoptOopif`。
- 验证：PR 说新增测试用脚本化的假 transport 驱动真实的 `BrowserContext` 和 `CdpConnection`，5 个场景在 `main` 上都失败，另在真实 headless Chrome 上验证。
- 代价：需要维护的状态更多（待定表、归属表），页面关闭和会话断开时要清理。
- 深挖：测试文件 `packages/extension/tests/understudy-context-oopif-adoption.test.ts`（PR 正文给出路径，我未打开）。

### 本主题小结

本期出现了三种给模型的接口。第一种让模型在可枚举的候选控件中选一个（Fastbrowse、先前读过的 Midscene System One），模型不输出坐标，代价是候选列表里没有的元素就点不到，控件过多时会中止（`observation_limit`）。第二种让模型输出归一化坐标的动作（Gemini）。第三种让模型写代码在持久环境中执行（OpenAI 文档的推荐路径，Mainplane 的工具面）。三者的共同点不是实验结论，而是可观察的设计分歧：同一周里两家模型厂商的文档分别把坐标动作和代码执行写在主路径上。本期没有找到把三种接口在同一任务集上对比的实测。

- [WebAnything](https://arxiv.org/abs/2610.37786)（2026-10-27）：从真实 URL 重建可重置的网页环境。Explorer-Builder 采集结构、资源和交互结果，独立验证器检查冻结的候选并触发局部修复。244 个站点、12,984 个已接受任务；用 5,856 条轨迹微调 Qwen3.5-9B，REAL 成功率 +9.9 点，WebArena-Verified Overall +13.33 点。
- [用于 GUI agent 的 iOS 在线稠密 RL](https://arxiv.org/abs/2610.39264)（2026-10-29）：规划 agent 与 UI grounding 模型分离，LLM 评委给步级稠密奖励加终局奖励，PPO，数百台并发虚拟 iOS 设备。自报 8B 模型在 Android 域外泛化相对 SFT 提升近七倍。
- [Where to Learn and How Far to Roll Out](https://arxiv.org/abs/2610.39251)（2026-10-29）：从成功专家轨迹建可复用检查点，用采样动作的 action disagreement 选 pivot 状态，阶段一在 pivot 做单步 RL，阶段二按进度扩展。自报 MobileGym 与 CUA-Gym-Hub 上环境交互减少 56% 至 61%。
- [TAM Task Advancement Memory](https://arxiv.org/abs/2610.37482)（2026-10-27）：执行时维护“已验证进展”状态，任务后把产生已验证局部结果的交互抽象成带输入、预期结果和验证条件的可复用操作，成功和失败任务都保留。自报 MobileWorld GUI-only 上仅进展状态即从 12.0% 到 28.2%；完整 TAM 相对最强基线 +17.6%，每个已解任务 token 减少 38.7%。属于轨迹复用方向。

## 给你的项目的启发（可选）

以下都是从本期条目推导的想法，不是条目本身的结论，没有在你的项目上验证过。

### 可直接借鉴

- yodo（演示一遍、agent 回放）：回放每一步点击前等待约 1 秒网络静止，并在不可逆操作前再检查目标位置。依据见“页面状态与点击时效”一节 What Does "Now" Mean 论文，数字是摘要自报。
- yodo：判断回放是否成功，不要只看“点击是否落在录制时的元素上”，还要看点击后的结果是否和录制时一致。依据见“点击落点”一节 Right Click, Wrong Box（同一动作可由多个元素触发）。
- TwoCursor：让人和 agent 的命令显示在同一个日志里、每个客户端选自己的标签页（pw-repl）；交接只接受真实点击来结束，页面脚本伪造不了（anomalyco/browse）。两者见“控制通道”一节，都是 README 层级的证据。
- TwoCursor：连接被替换时把动作结果标为“未知”并且不自动重放（TheGitAI 文档，子代理读取）。人在中途接手时，上一条指令是否执行过有可能不确定，这个设计对应的就是这种情况。

### 有冲突需权衡

- TwoCursor 把请求和 DOM 记录成结构化数据，需要扩展有较宽的权限。anomalyco/browse 的扩展权限包括 debugger、tabCapture、scripting 和全站点访问；agent-bridge 默认不附加 chrome.debugger。是否显示“正在调试”横幅，是可见性和能力之间的取舍，要读完各自实现再决定。
- 把站点经验写成文档、按开关注入（browser-harness #959），和 Skyvern 把演示当作 grounding 信号的思路不同：前者是文本，后者直接用演示。yodo 选哪种，或者两种都用，本期材料不足以判断。

### 值得做的小实验

- 用 yodo 已有的录制回放，在每一步点击前加“等待网络静止 1 秒”的开关，比较回放成功率和总耗时，与 preflight-bench 的结论对照。
- 用 Right Click, Wrong Box 的思路，对 yodo 的一条录制，在同一页面上试几个等价元素的点击，看结果是否相同，据此决定录制时要不要保存多个候选选择器。

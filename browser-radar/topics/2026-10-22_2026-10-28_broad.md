## 本期概览

这一周最清楚的走向是：大家都在重新划分“谁决定、谁执行、谁保存”的边界。browser-use 草案把动作执行交给模型写的 CDP 代码，Midscene 把简单动作交给便宜的专用模型，录制回放类项目把一次成功沉淀成不再调用模型的流程，安全修复则集中在“模型或页面能不能改策略”。另一条线是观察和评测的可信度：被遮挡的元素、过期的截图、取平均的奖励、按框判分的点击，都在偷偷改变结论。

覆盖了 GitHub、厂商与产品、工程博客、论文（只读摘要）和社区五个渠道，分成 7 个主题。这一版是“广泛版”，把旧文档因范围太窄而没收的 computer use、视觉 grounding、评测和厂商内容补上，旧文档已写的项目只在“其他”里一句话带过。

窗口里厂商和官方工程博客的有机制内容很少，许多重要更新在窗口前，论文渠道只拿到摘要，社区、Reddit、X 和中文社区基本没覆盖。因核实不过而明确剔除的只有 1 条（ruyiJS，用途是绕过防护且不可审计），另有一批因证据过浅或机制重叠只列在“其他”里。大部分细节是子代理转述，我亲自核对的部分已在“待验证与存疑”里列出。

## 1. 动作接口与引擎架构：让模型写代码，还是让专用小模型选动作

这一期有两条方向相反的架构动作：browser-use 草案把整个规划器换成「模型直接写 CDP 代码」，Midscene 则把简单动作交给便宜的专用决策模型。两者都在重划「谁来决定下一步」的边界。

### 本期新内容

**1.1 browser-use 草案 PR #6202：用 Pi 引擎取代 Python 规划器（架构更新，未合并）**

- 来源：[browser-use/browser-use#6202](https://github.com/browser-use/browser-use/pull/6202)，相关仓库 [browser-use-pi](https://github.com/browser-use/browser-use-pi)。Browser Use 团队，GitHub。PR 创建于 2026-10-24（API 核实），状态仍是未合并草案（我 10-28 查询时）。
- 证据等级：PR 正文由我亲自通过 API 读到；browser-use-pi 的 docs/browser.md 我亲自读到。我没有读 #6202 的 diff，Python 到 Node 的桥接层没核对。
- 解决什么问题：Python 版的规划器、DOM 序列化器、各家模型适配层和 Rust 测试版体量大、维护重叠。PR 称生产源码从 66,924 行 Python 降到 11,740 行（Python 加 TypeScript）。
- 怎么做的：
  - 模型只有一个 `javascript` 工具，背后是持久的 Node REPL，变量和 await 跨单元保留。
  - REPL 里暴露 `page.snapshot()`（带 backend ID 的无障碍树节点）、`page.evaluate`、`page.clickAt(x,y)`（真实鼠标输入）、`page.cdp(method, params)`（带类型的原生 CDP）和 `tabs.*`。
  - 文档给的点击配方：在快照里找到按钮并确认可用，用 CDP 滚动到可见，读盒模型算中心点，再 `clickAt`，之后检查结果，因为遮罩层可能吃掉了这次点击。
  - 被删除的有旧规划器、Watchdogs、DOM serializer、各模型 provider 包装和 Rust 版。默认浏览器改成云端浏览器，默认模型改成网关别名。
  - 失败恢复从不自动重放动作；CDP 超时也不代表页面上的操作已经停止。
- 关键取舍与代价：
  - 动作执行从固定工具集挪到「模型写代码」，通用性上去了，可审计和可约束性下降。文档明说生成的 JS 跑在子进程里，但那不是安全沙箱，代码仍能读文件和访问网络。
  - PR 自己写明：基准 BU Bench V2.1，每组固定 200 题，Pi 62.905 对迁移版 58.350，但「不能证明性能持平」。两组用的是同一个外部模型，没经过新网关。
  - 旧的 Python 安全 Watchdog 一并被删，依赖域名白名单的用户会遇到行为变更（相关的安全问题见主题 4）。
- 和已知做法的关系：与 Playwright MCP、Stagehand 这类「固定工具集加快照 ref」的路线相反；更接近让模型直接写自动化脚本的路线。
- 想深挖：browser-use-pi 的 src/prompt.ts（教模型的配方）、docs/sessions.md；#6202 里桥接层的 diff。
- 现状：草案，需要配套的 Go 网关 PR、预发布检查和一轮新的匹配基准后才会发布。

**1.2 Midscene 接入 System One 决策模型：一次请求同时返回动作和坐标（架构更新）**

- 来源：[midscene#3295](https://github.com/web-infra-dev/midscene/pull/3295)（合并于 2026-10-23，API 核实）、[#3301](https://github.com/web-infra-dev/midscene/pull/3301)（合并于 2026-10-27，子代理读取）。Midscene 团队，GitHub。
- 证据等级：#3295 正文我亲自通过 API 读到；#3301、模型文档和下面的社区原型是子代理读的，我没有核对。没读 Midscene 的 diff。
- 解决什么问题：用大型生成模型每一步都「看图加输出坐标」又慢又贵。
- 怎么做的：
  - 把 Jev 集成拆成调用、定位、布尔判断、规划几个模块。规划按动作空间推导：简单动作由 Jev 直接选，复杂动作交给默认大模型，并附一条建议。
  - 规划和定位用同一个 Jev 模型且同一个 Base URL 时，单目标的简单动作一次请求同时返回动作和目标框，执行时直接复用坐标，省掉第二次定位请求。deepThink 下关闭此优化，模型或提供方不同时也保持分开定位。
  - 动作元数据新增 `supportedBySystemOne`，选项超限时回退到默认路径。
- 关键取舍与代价：
  - PR 自己承认 Jev 可能过早把未完成的任务判成已完成，这次没有加完成校验。
  - 子代理读到的补充（未核对）：Jev 的 Box 接口总会返回一个框、没有「找不到」，需要配合一个是非题判断目标是否存在；这种方案需要你自己准备候选项，更像脚手架。
- 同类社区原型（子代理只读了 README）：[System-One-Computer-Use](https://github.com/brainstormity/System-One-Computer-Use)，2026-10-23 创建，循环是截图、同时问动作和目标、用 pyautogui 执行；置信度低于 0.5 就停手。自述为原型，只在一个 macOS 环境测过。
- 想深挖：#3295 里 `callSystemOneAI` 与 `callGenerativeAI` 的拆分，以及单次请求复用坐标的条件。

### 本主题小结

同一周内出现了两个相反的取舍：一边放权给模型（写代码、直接发 CDP），一边收权给专用决策器（便宜、快、但要自己备候选项）。两边的共同点是都在拆掉「每一步都让通用大模型看图输出坐标」的默认做法，而且两条的安全或完成度保障都明说没做完：Pi 不是沙箱，System One 没有完成校验。

## 2. 观察结果的可信度与时机：元素列表会撒谎，截图会过期

这一主题的共识是：agent 点错往往不是「看不懂」，而是观察结果和真实页面状态对不上。两个由我亲自读过 README 的个人项目分别量化了「被遮挡」和「页面还在加载」两类对不上的情况，样本都小，但机制清楚。

**2.1 glance-occlusion：给观察结果加「被遮挡」标记（新项目）**

- 来源：[pedapudibhargav/glance-occlusion](https://github.com/pedapudibhargav/glance-occlusion)，个人，GitHub。仓库创建于 2026-10-24（子代理用 API 读到，未核对），0 星。
- 证据等级：读过 README（我亲自读，经 WebFetch 摘要）。子代理另读了 probe/structure.js 的部分代码，我没有核对。实验数字是作者自测，未复现。
- 解决什么问题：agent 拿到的元素列表里，被同意弹窗盖住的元素和能点的元素长得一样，agent 选对目标却一直点不到，白白烧步数。
- 怎么做的：
  - 用 `elementFromPoint` 做命中测试，让合成器告诉你哪个元素真正收到点击，约 3 毫秒，不受文档边界限制。
  - 根据 README，对比对象是 browser-use 基于 CDP 绘制顺序（paint order）的遮挡检测：绘制顺序是按文档算的，跨域 iframe 里的弹窗不会在顶层文档的快照里产生覆盖盒，所以在 BBC、FT 等站点召回率只有 0.00 到 0.17，纯 DOM 站点上是 0.84 到 0.95。
  - README 称 CDP 的完整无障碍树、分帧合并和 Playwright 的 `aria_snapshot` 在所测的 8 个站点上都没有表达遮挡。
  - 观察文本最前面写一行 OVERLAY 说明，把被盖住的元素 id 折叠成短列表。
- 实验结果（作者自述）：26 个任务、11 个真实站点，普通列表解出 4 个，带遮挡标记解出 19 个，平均步数从 5.23 降到 3.38，观察 token 几乎不变（3,008 对 2,887）。第二个模型和确定性 HAR 基准上方向一致。
- 关键取舍与代价：
  - 任务集小、站点是挑的、基准是作者自建；HAR 回放 11 个里有 1 个没复现出遮罩层。
  - 负面结果写得诚实：把观察结果压缩成只保留可达元素，虽然省 80% 字符，成绩从 36/40 降到 30/40；注明项目内记录了三十处对自己早期结论的修正。这说明结论不稳，按「有趣的假设」对待。
- 和已知做法的关系：对立。主题 1 的 Pi 删掉了 DOM serializer，按 README 的说法 browser-use 原有的遮挡检测就是那里面的绘制顺序逻辑，迁移之后这个能力有没有带过去，我没有核实。
- 想深挖：probe/structure.js 的 `isObstructive` 和公告阈值；scripts/paint\_vs\_hit.py 里和绘制顺序方法的对比。

**2.2 preflight-bench：点击前检查「屏幕还是不是我规划时的样子」（新项目）**

- 来源：[multimodal-ai-engineering/preflight-bench](https://github.com/multimodal-ai-engineering/preflight-bench)，Vasundra Srinivasan，个人研究，GitHub。仓库创建于 2026-10-27（子代理用 API 读到，未核对）。
- 证据等级：README 我亲自读（WebFetch 摘要）；README 自己说机制在 `src/anchored/`，子代理读了 check.py 的头部，我没核对。论文数字未复现。
- 解决什么问题：computer-use agent 截图、规划几秒、再点击，页面中途变了就点错。作者认为风险主要来自页面加载，而不是规划时长本身。
- 怎么做的：
  - 测量：31 个公开页面上，页面刚打开 1 秒内规划的点击有 17% 会失效，页面完全加载后 30 秒内只有 0.4%；等网络空闲（中位数 1.2 秒）可降到 0.5%。
  - 检查（据 README 概述和子代理读到的代码头部）：用前后两帧的灰度差做运动遮罩，在计划位置做带遮罩的归一化互相关（NCC）；不在原位就在窗口里重找，找到唯一峰就微调点击位置，否则重新规划。
  - 像素比较检出 82% 的失效点击，误报 4%，耗时 0.3 秒；README 称某大模型能匹配检出率，但误报约三倍、延迟约八倍；2B 到 4B 的小视觉模型检测「目标有没有动」不可靠。
  - README 还说，他们看过的 10 个开源 agent 里有 8 个的等待规则会让超过 1% 的点击失效（自述，没有列出是哪些）。
- 关键取舍与代价：基准页面是作者生成的虚构页面，真实页面截图不发布；商业页面数据来自 HTTP Archive 的抓取，没有直接访问，数字是下限；渲染只在特定 Chromium 构建上确定；需要额外一帧（约 200 毫秒）；十四个预注册假设里八个被证伪（README 自述）。
- 想深挖：src/anchored/check.py 的阈值参数；src/harness 里「何时值得先检查」的盈亏平衡公式。

**2.3 两篇论文：WaitLens 与 Hagasu（只读摘要，子代理读取，未核对）**

- [WaitLens](https://arxiv.org/abs/2610.32482)（2610.32482，2026-10-23，美团工业测试流水线数据）：用带「等待结束时刻」标注的加载轨迹微调轻量 VLM，从时序观察判断「要不要继续等」。摘要报告固定等待占采样间隔时间的 42.3%，等待时间的 62.9% 发生在界面已加载之后；「继续等待」判断准确率 86.08%（基座 54.13%）。只针对移动端测试，一家公司的数据。
- [Hagasu / Chart the Invisible](https://arxiv.org/abs/2610.35237)（2610.35237，2026-10-26）：小屏上目标在视口外时，训练一个「可滚动区域感知」模型让 agent 先探索隐藏区域再选动作。摘要称需要滑动的情形中 47.8% 错选了点击，识别可滚动区域准确率 78.5%，给 9 个 GUI agent 加上它后探索依赖任务的平均完成率从 64.8% 升到 82.7%。主要针对移动端。

**3.1 AdaGround：免训练的自适应缩放加验证器**

- [arXiv 2610.36874](https://arxiv.org/abs/2610.36874)，Bingchao Wang 等（2026-10-27 09:12 UTC），代码 github.com/bcwang-sjtu/AdaGround（未验证）。
- 解决什么：高分辨率屏幕上小目标 grounding 失败，现有 zoom 不按目标大小缩放、不验证、也不回头重来。
- 怎么做（摘要所述）：(a) 按模型自己估计的目标大小设定放大倍数、视野和 zoom 深度；(b) 用「标记点击位置」的 Yes/No 验证器保留或拒绝每次 zoom、在多条 zoom 链中选择、触发重新 grounding，并用存在性查询决定何时弃权；(c) 电子表格单元格用行列表头组合定位。
- 结果（摘要原数）：Qwen3-VL 上相对基座在 OSWorld-G 和 ScreenSpot-Pro 提升 7.4 到 20.6 个点，留出的 UI-Vision 上增益保持。
- 代价：验证器每一步多一次模型调用，摘要没量化延迟。
- 想深挖：验证器提示词设计和弃权阈值。

**3.2 LBS：把 GUI grounding 当成「主动观察」的监督来源**

- [arXiv 2610.37093](https://arxiv.org/abs/2610.37093)（Learning to Look Beyond Screens，2026-10-27 11:56 UTC），代码 github.com/inclusionAI/UI-Venus/tree/LBS（未验证）。
- 怎么做：先用教师生成的 grounding 轨迹做 SFT，再用 RL 优化多轮「裁剪加检查」决策。作者分析认为 SFT 建立「视觉检查原语」，RL 提高原语的使用效率；增益称可迁移到 PerceptionBench、HR-Bench、ChartQAPro。
- 代价：基座较大（Qwen3.5-35B-A3B 和 Qwen3.8-27B，页面所列），摘要没给具体分数。
- 想深挖：RL 奖励设计、crop 动作空间定义。

**3.3 GUI-JEPA：无解码器的候选动作打分策略（移动端）**

- [arXiv 2610.36877](https://arxiv.org/abs/2610.36877)（2026-10-27 09:17 UTC），代码 github.com/bcwang-sjtu/GUI-JEPA（未验证）。
- 怎么做：在无标注 GUI 截图上预训练 JEPA 编码器，用「动作与区域条件的潜变量预测器」把屏幕潜变量变成每个候选动作的潜变量，再由轻量头与指令一次批量打分，不解码任何 token。
- 结果（摘要原数）：AndroidControl 上同一 GPU 比自行微调的 Qwen2.5-VL-7B 快 2.8 到 4.0 倍，用 6% 的参数达到其分布内准确率的 86% 到 92%。
- 代价：只能在预先枚举的候选动作里选，不是自由生成；摘要报告「随机初始化的预测器与预训练的一样好」，说明预测器是为决策训练的。
- 想深挖：候选动作如何生成、分布外的差距。

**3.4 GUIFlow：免训练的增量推理**

- [arXiv 2610.34959](https://arxiv.org/abs/2610.34959)（2026-10-26 07:25 UTC）。
- 怎么做：相邻步的观察和历史大量重叠，却每步重算视觉编码、prefill 和解码。方法是把历史 KV 状态位置对齐后注入当前上下文，用变化信号选择性更新当前观察状态，并把上一步的动作输出当作推测解码草稿交给目标模型验证。
- 结果（摘要原数）：离线多图基准几何平均最高 3.39 倍加速，OSWorld 在线闭环最高 3.49 倍，任务表现与稠密基线大致相当。
- 代价：需要改造推理引擎，闭源 API 用不上。
- 想深挖：KV 位置对齐细节，以及何时判定页面变化足够大而放弃复用。

**4.3 Evervault Browser Tokens：在网络边缘替换凭据**

- 来源：[evervault.com/products/browser-tokens](https://evervault.com/products/browser-tokens)。Evervault，产品页。页面无发布日期，HN 提交时间 2026-10-23（子代理用 HN Algolia 读到），所以首发日期未核实。

## 5. 录制、回放、API 重放与轨迹复用

这一周的共同趋势是把“一次成功的执行”沉淀成可以不再调用模型的东西，分三条路：页面动作回放（指纹定位）、绕过界面直接重放站点自己的 API、以及在轨迹上逐步判断“重用、调整还是丢弃”。三条路的共同难题是不变的前提：站点改版了怎么办。

**5.1 Flintrail：实时驱动、录制、无模型回放、失败处修复（新项目）**

- 来源：[Soflutionltd/flintrail](https://github.com/Soflutionltd/flintrail)，Soflutionltd，GitHub。仓库创建于 2026-10-26（子代理用 API 读到，未核对）。
- 证据等级：README 我亲自读过（WebFetch 摘要）；子代理另读了 src/recorder.ts、flows.ts、engine.ts、cdp-filter.ts、server.ts，以下“源码级”细节是子代理转述，我没有核对。
- 解决什么问题：浏览器 MCP 每次点击都是一次模型轮次，同一任务明天要重新付全价。
- 怎么做的：
  - 实时：agent 把一串动作批量提交，拿回带引用的紧凑快照。
  - 录制（README）：同样的动作被存成流程步骤，每步存目标元素的指纹（测试 ID、ARIA 角色和名称、可见文本等）而不是脆弱的选择器，值可变成 `{{variables}}`。子代理读到的源码补充：password 类型字段明确不录。
  - 回放（README）：不调用模型，按从最稳定到最不稳定的顺序尝试指纹；失败时停在该步、把页面交还给 agent，只修这一步，并用 `repairFrom` 重录后面的步骤。
  - API 重放（README）：抓取站点自己的 fetch/XHR 调用，在页面内用同一个 cookie 和会话重发，跳过渲染和点击。
  - 浏览器模式：attach（连专用 Chrome for Testing，保留登录态）、launch（持久化 profile）、extension（Chromium 125+，无需调试端口，还能录用户手动演示）。README 称默认拒绝连接个人浏览器。
- 代价：基准是作者自测（五步任务、十次中位数、工具侧耗时：比原始 Playwright 脚本多约 50 毫秒，Playwright MCP 多约 260 毫秒；API 回放 114 毫秒）。`eval` 和 `request` 动作以页面自身权限执行，回放 API 请求会用已登录的 cookie，读写登录态的面比较宽，用之前要自己审。
- 想深挖：engine.ts 的 `resolveTarget` 候选顺序；recorder.ts 的 `addDemoStep`（扩展里用户手动演示如何转成步骤）。

**5.2 sidedoor：把录到的 Web 应用自己的 API 调用转成带类型的 MCP 工具（新项目）**

**5.3 三篇论文：轨迹复用与记忆（摘要级）**

- [Reuse, Rewrite, or Reject](https://arxiv.org/abs/2610.31712)（2610.31712，2026-10-22 03:09 UTC，子代理读摘要）：图文模板——图建模 UI 状态和动作转移，文本描述任务意图、流程结构和带类型的槽位。record-template-replay 框架用当前指令和实时 UI 状态逐个转移决定重用、调整或丢弃。AndroidWorld 上五种基座 agent 平均少用约 80% 的 LLM 推理 token。移动端。

### 本主题小结

桌面侧和浏览器侧都在走向“不抢用户输入”的通道（AX 动作、私有显示器、后台标签页），但各自的边界都不完整：“不抢焦点”不等于“界面不变”，“隔离输入”不等于“隔离文件和网络”，“后台标签页”却用了真实登录态。一个倾向：双方都在把登录和验证（passkey、验证码、Bitwarden）当作需要专门通道的事情处理。

## 7. 评测的可信度：分数怎么算、错误怎么归因

这一周有三条证据说明常用分数的计算方式有问题：BrowserGym 的奖励可能把部分完成算成部分分数，ScreenSpot 类基准把效果相同的点击判为错，完成率也不区分“出错后能不能恢复”。两条由我亲自核对了原始页面。

**7.1 BrowserGym issue #412：WebArena-Verified 的奖励把多个评估器得分取平均**

- [ServiceNow/BrowserGym#412](https://github.com/ServiceNow/BrowserGym/issues/412)，作者 salma2vec，创建于 2026-10-23，状态 open（我用 API 亲自核对）。没读相关 PR #413 的 diff。
- issue 称 `WebArenaVerifiedEvaluator.__call__` 在任务有多个评估器时返回各评估器分数的均值，而官方 webarena-verified 的规则是所有评估器都通过才算 1.0，任何一个失败或出错就是 0.0。所以一个对一个错一个的任务在 BrowserGym 里得 0.5，在基准里算失败。作者认为这会使 AgentLab 报的平均奖励偏高。812 个任务里 488 个有两个或更多评估器（391 个两个，97 个三到十一个）。

**7.2 Right Click, Wrong Box：按“点击的结果”给 grounding 打分**

- [arXiv 2610.36831](https://arxiv.org/abs/2610.36831)，Xiaokang Yuan 等，2026-10-27 08:30 UTC。摘要我亲自读过。
- ScreenSpot 类基准只在点击落在单个标注框内才算对，但很多界面用多个元素提供同一个动作。作者把“正确”重新定义为“产生和标注目标相同的结果”，探针在实时 Web 应用里执行并给约 1000 次点击打指纹，得到结果图和执行裁判，不需要新标注。
- 结果：在一个代码托管站和一个网店里，框判错的点击里约五分之一到三分之一实际达到了预期结果；对 11 个模型在 ScreenSpot-v2 上审计，修正幅度 0.2 到 1.8 个点，与业界汇报的模型间差距同量级。
- 代价：只在两个实时站点验证；3B 的 GRPO 实验里，奖励里承认等价点击并没有带来稳定增益。作者称会发布探针、结果图、审计和全部预测，页面未给 URL。
- 对自己做 agent 的人有用：按“结果指纹”判断两次点击是否等价，可以直接用来判断访问后的验证。

**7.3 其他摘要级条目（子代理读摘要，未核对）**
